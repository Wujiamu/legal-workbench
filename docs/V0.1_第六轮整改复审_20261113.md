2026-11-13。受检范围为当前法律工作台目录及第六轮交接。**第五轮提出的三个原始场景通过复测。整体签收仍有三项 P2 待处理。**

| 优先级 | 发现与证据 | 关闭标准 |
|---|---|---|
| P2 | **文件发布成功后，批次提交前的失败仍会留下无引用文件。** 在上传审计调用处注入异常，此时文件已写盘，数据库尚未提交。新连接查到 0 个批次、0 个任务，磁盘有 1 份无引用文件。用同请求键和相同文件重试成功并重新纳入引用。清理的异常处理只包住上传循环，任务创建、审计与提交在其外。[上传收尾](../backend/src/legal_workbench/imports.py#L477) | 让失败处理覆盖发布到提交的实际边界。复测审计和提交前故障，确认无半成品批次、请求键可重试、无遗留文件。清理前保留对已提交引用的核查。 |
| P2 | **备份维护开始时，上传回滚后的清理和完整性标记被跳过。** 在独立连接中，将维护标志设在失败批次回滚之后、取清理锁之前。上传实际返回 `maintenance`，留下 1 份无引用文件；触发失败的既有损坏对象仍标为 `ok`。清理锁入口先检查维护标志并抛错，掩盖了上传原本的完整性错误。这是用真实 PostgreSQL 控制维护标志时序的结果，本轮未并行运行实际备份进程。[清理入口](../backend/src/legal_workbench/imports.py#L332) · [维护检查](../backend/src/legal_workbench/db.py#L117) | 保持备份期间的文件互斥。明确并验证清理、完整性标记在维护结束后的完成方式。原上传错误应可诊断，维护结束后不留无引用文件或错误的完整性状态。 |
| P2 | **改名成功的迟到响应会按旧筛选刷新材料列表。** 在「全部」中发起甲的改名，切到「乙分类」并等列表仅显示乙，再让甲成功返回。受控组件测试发现「乙分类」仍处于选中状态，甲却重新出现。保存回调用的是发起操作时捕获的列表加载函数，其筛选和页码可能已过期；列表响应直接写入当前界面。[改名回调](../frontend/src/components/MaterialDetail.tsx#L147) · [列表加载](../frontend/src/pages/CaseWorkspacePage.tsx#L62) | 成功写入触发当前案件和当前筛选条件下的刷新，旧请求结果不得覆盖当前列表。覆盖切换分类、翻页时的迟到回包，同时保留切回原材料能看到更新的回归。 |
