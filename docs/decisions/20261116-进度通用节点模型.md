# 进度通用节点模型

状态：2026-11-18 补记（P0）。决定在 2026-11-16 总体计划第二至五节作出并经用户确认；P1 原型按此实现，P2 后端沿用。适用范围见 [办案进度可视化](../changes/20261116-办案进度可视化.md)。

## 问题

进度模型要表达真实诉讼的全部形态，且未来新增案件类型时是"增量"而不是"推翻"。用专利/知识产权诉讼的常见情形检验：一审中提管辖异议并上诉（程序嵌套子程序）、侵权诉讼同时被告提无效宣告（一案多条并行程序）、无效决定导致诉讼中止（非包含关系）、庭前多次证据交换每次再分解（工作/事件可再分）、二审/发回重审/再审/执行（按需插入）、庭审时间与上诉期（日期期限）、证据整理关联材料与分析成果（引用业务对象）、Agent 改阶段承办人不同意（撤回需知修改前值）、以后加 FTO/无效/OA 答复（种类与模板不能写死）。

## 可行选择

1. **固定层级 + 进度条**：案件→固定几个阶段，阶段下不能再分。无法表达嵌套程序、并行程序与再分解，新案件类型要改表结构。放弃。
2. **从材料/任务推断进度**：不单独建进度模型，由解析任务与分析状态推导。进度是承办人的主观登记，推断不出"当前在哪个阶段""下一步做什么"，且与材料处理耦合。放弃（期限登记沿用 2026-11-14 决定）。
3. **通用树 + 规则配置 + 类型化关系 + 变更记录**：节点是不限层级的树，层级与种类由配置约束；非包含关系用独立关系表；所有修改留变更记录。采用。

## 决定

三个结构性结论（以后很难改，故在此固定）：

- **节点是一棵不限层级的树（包含关系），另加类型化关系表达非包含关系。** 层级深度、哪些节点能放在哪里，由规则配置决定，不由数据库结构或界面组件决定。
- **所有修改留下"修改前/修改后"的变更记录。** 这是撤回、待确认、历史时间线的共同基础。
- **视图和数据彻底分开。** 同一份数据可以有多种画法（大纲、图形、以后的时间轴/甘特），加画法不动数据。

关键口径（K 编号沿用总体计划）：

- **K1 层级只在规则配置**：`containment` 映射父种类→允许子种类（根用 `case`）。数据库只校验非空与组合外键，不写死层级。
- **K2/K3 种类与状态按配置**：`kinds` 定义种类、合法状态、默认状态。"当前阶段"= 状态为进行中的阶段，同一程序内最多一个（set_active_stage 一并调整原阶段）。
- **K4 非包含关系独立表**：起点、终点、类型；类型由配置定义，首版界面只开放"引起""关联"。包含关系永不暗示先后或依赖。
- **K5 变更记录**：每命令同事务写一条，含每个受影响对象的修改前/后值与修订号；Agent 变更待确认，人工可确认或撤回；撤回是反向命令，节点已被后续修改时拒绝。
- **K6 模板由片段组成**：片段是一棵小树，建案实例化默认片段，之后可在规则允许位置插入任意片段；片段放后端配置并带版本。新案件类型 = 新片段集。
- **K7 业务关联独立表 + 组合外键**：首版可关联材料、分析成果、标注；案件隔离由数据库强制。
- **K10 布局坐标不入库**：图形视图由 elkjs 计算，是视图状态。
- **K13 收起是视图状态**：不写入数据，两种视图共享。
- **K14 建案实例化默认片段**：已有案件在迁移时补实例化。
- **K15 期限暂留案件 JSONB**：节点带日期字段，以后把期限迁为节点属性是增量迁移，避免与刚验收的期限功能同时改两处。

## 放弃的方案与理由

- 固定层级/进度条：见上，无法表达嵌套与并行，扩展即推翻。
- 推断进度：进度是主观登记，推断不出当前阶段与下一步。
- 拖拽改层级、手动排版持久化：首版不做（K13），移动走 move 命令；布局另建视图状态表是增量。
- 多用户协作：需用户与权限，另立项，当前不做占位。

## 后果

- 第三四层节点、新种类（保全/鉴定）、新案件类型（FTO/无效/OA）、并行程序与中止关系、时间轴/甘特视图、任务依赖与提醒、模板编辑器、统一待复核收件箱、实时推送——全部是配置或增量，不动表结构。
- 结案归档是**案件级操作**（树外按钮），不是进度节点（2026-11-16 用户反馈第四轮取代原 Q1 树中的"结案归档阶段"）；正式归档语义落案件域。
- 换图形库只替换图形视图，局部替换。
