## 一、背景与问题

1. 工作台已上线跨案期限时间轴、办案程序进度图、案件主体关系图与诉请金额瀑布图（`WaterfallChart`），后续还将按需横向扩展多轨事实时间线、资金流向图、争点攻防树、证据覆盖矩阵等视图。
2. 在内部办案思考与外部呈递之间存在天然张力：
   - **自用构图时**需要界面极简，不能把画布堆满证据编号、页码和脚注；
   - **对外沟通（客户汇报）或当庭说明时**必须做到每项关键陈述均有明确可追溯引用，且严禁把未核实推测、未确认 Agent 提案、内部办案备注或过时证据编号带出工作台。
3. 同时，主体关系图等结构化视图不应只靠人工逐笔录入或外部 Agent 黑盒生成，必须尽量把**确定性提取、全案防漏、跨文档强指纹碰撞和对外引用组装**收归程序完成，把**法律语义核验**留给外部复核 Skill 与承办人。

## 二、决定

### D1：所有图表统一实行“一源三态”呈现与导出机制

图表底层数据与展示密度解耦；任一支持对外导出的图表共享同一套三态呈现/导出配置（Render / Export Profile），由程序确定性渲染，不手工抄改两套图：

| 模式 | 适用场景 | 画面引用密度 | 程序确定性处理 |
|---|---|---|---|
| **内部工作态**（默认） | 承办人日常阅卷、梳理与编辑 | **极简**：画布不堆满编号与长脚注，仅保留轻量状态/有无出处标记，点选后在侧栏展开详情与原件 | 完整展示全部状态（含待查虚线、已排除、内部备注、Agent 待确认项） |
| **客户沟通态** | 向客户汇报案情、确认方案或商业决策 | **适度引用**：图面用精简角标（如 `[1]` 或 `[证据1-2]`），完整明细自动收至图底或附页脚注 | 自动过滤 `pending` 未确认提案、内部备注与已排除项；输出图例、快照版本、导出日期与“待查项说明”水印 |
| **当庭呈递态** | 交法庭辅助说明、举证质证或附于代理词 | **严格强引用**：统一调用 `evidence_catalog.resolve_labels` 实时解析最新正式编号，图面放紧凑角标，**并自动同步生成配套《图示引用索引附表》**（Markdown/CSV） | 强制执行 D2 程序硬门禁；禁止包含内部备注与未确认项；强制锚定一份不可变快照（或当前导出冻结包）以留存当日编号 |

### D2：划清“工作台程序硬门禁”与“外部 Skill 实质复核”的职责边界

工作台保持本地、离线、无内置 LLM 且**不做“法律结论生成器”**的既定边界。对外出图的复核机制拆为严格互补的两层：

1. **第一层：工作台内置程序硬门禁（确定性形式校验）**
   - 导出对外版（尤其当庭呈递态）前，共享服务层必须自动校验并报告：
     - 是否混入 `pending` 未确认的 Agent 变更；
     - 纳入展示的元素是否存在无任何出处、或所引材料尚未编入已确认证据目录（“未编号”）的情形；
     - 是否有 `suspected`（待查）元素或内部 `note` 被误纳入当庭范围；
     - 所引片段/材料是否已被软删、解析存在失败/告警，或相对目标快照已发生目录编号漂移。
   - 当庭版遇阻断级问题默认拦截（显式豁免须由人工逐项确认并记录）。
2. **第二层：外部复核 Skill + 人工终审（法律实质与策略核验）**
   - 工作台通过统一只读 CLI/MCP 命令（`export-chart-audit-bundle`）吐出标准审计包：**图表展示断言清单 ＋ 每条断言关联 `source_ref` 的实际原文文本 ＋ 当前正式证据编号 ＋ 硬门禁报告**。
   - 外部 Agent 按复核 Skill 消费该审计包，执行程序无法替代的实质核查：文图逐字一致性（主体、金额、日期、方向、认缴/实缴）、证明力是否越界或张冠李戴、与起诉状/代理词口径是否矛盾或存在不当自认风险，输出结构化复核报告供承办人拍板。

### D3：全图表统一出处引用协议

所有既有与新增可视化图表（关系图、诉请图、未来时间线/资金流/争点树/证据矩阵）在挂载证据出处时：
- 一律只存稳定引用 `(segment_id | material_id | annotation_id, proves)`，**绝不把 `证据1-1` 等编号文本作为事实真相写入业务字段**；
- 展示、预检与导出统一复用 `evidence_catalog.resolve_labels()` 解析现行编号；
- 跨案引用继续由 PostgreSQL `(case_id, …)` 组合外键与服务层 `case_mismatch` 双重拦截。

### D4：横向反过度可视化红线与明确淘汰边界

为保持工作台“精而非泛”，确立以下两条长期边界（避免后续会话重复推翻重来）：

1. **以下 6 类界面坚决不强行图形化**，保持列表、表格、表单或文本阅读器形态：
   - 材料目录、导入队列、分类与取得方式管理；
   - 证据目录编写与排号（证据与事实的对应交由二维矩阵，不画目录节点图）；
   - 全文/金额/日期/编号检索命中列表；
   - Agent 待复核收件箱（采用紧凑列表 + 原文对照，不做大卡片看板墙）；
   - 案件概览字段、工时补录、客户同意流、审计日志；
   - 分析与代理词正文写作（以 Markdown + `source_ref` 为主，按需嵌入上述图表导出的 PNG/SVG）。
2. **明确淘汰的 8 项方案（不立项）**：
   - 让律师手写 DSL 语法编译出图（过度程序员化，有 Agent 可替代）；
   - 律师自建可视化提取配方市场（过度工程师化，不符合单用户律师习惯）；
   - X 光逐页扫描实时生长动画（Demo 型伪透明，不如静态覆盖异常清单有效）；
   - 传统依存句法/脆弱正则硬抽正文自然语言关系（面对扫描 OCR 案卷极易失真）；
   - 纯共现矩阵直接自动生成整张“案件骨架图”与社群聚类（诉状同页共现易成全连接毛线球）；
   - 复杂法律要件白盒逻辑推理机 / Datalog（违背“不做法律结论生成器”原则且易误报；纯粹股权穿透等算术计算另归远期 P3）；
   - 合同文本同源基因 / PDF 作者元数据碰撞（扫描件居多的诉讼案卷中失效且通用模板误报极高）；
   - 闪卡式（Tinder）高速刷线索攒图（低信噪比下体验折磨，与既有复核列表割裂）。

---

## 三、后果与复用要求

- 后续任何新图表模块立项时，必须在变更单中声明其接入 `chart_export`（一源三态与审计包）的方式，不得再为单一图表私有实现重复的编号解析或导出校验逻辑。
- 涉及工程量较大或维护成本较高但具备明确展示/效率价值的方案（如 GIS 风格同坐标多图层客户展示视图、可视化提取步骤画布、高频固定格式专项适配器）**不纳入淘汰清单**，按优先级沉淀在 [横向可视化与二三期图表演进路线](../changes/20261122-横向可视化与二三期图表演进路线.md) 中按需启动。
