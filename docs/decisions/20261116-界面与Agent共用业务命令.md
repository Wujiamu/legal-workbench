# 界面与 Agent 共用业务命令

状态：2026-11-18 补记（P0）。决定在 2026-11-16 总体计划第一节作出并经用户确认；P1 原型按此实现，P2 后端沿用。适用范围见 [办案进度可视化](../changes/20261116-办案进度可视化.md)。

## 问题

办案进度要同时被两类操作者修改：承办人在网页上点击，Agent 通过 MCP/CLI 登记。如果各自直接改数据，会出现三个后果：规则校验各写一份并逐渐分叉；无法区分"谁改的"，Agent 的修改混进人工修改里无法复核；撤回一次修改时不知道修改前是什么。

## 可行选择

1. **整图保存**：前端把整棵进度树序列化提交，后端整体替换。实现简单，但并发覆盖无法避免，Agent 与人工互相抹掉对方修改，且无法定位"哪一处是谁改的"。放弃。
2. **各入口各写一套逻辑**：网页走 HTTP 直接改表，Agent 走 MCP 另写一套。短期快，但校验、审计、变更记录三处重复，必然分叉。放弃。
3. **业务命令 + 共享服务层**：把每个操作定义为一条命令（add_node、set_active_stage、revert_change…），网页、MCP、CLI 都调用同一个服务函数，只有 `actor` 与 `entry` 不同。采用。

## 决定

- **数据库是唯一事实来源，图形界面是它的投影。** 人工点击也是先写库、后显示；前端不持有权威状态，命令成功后以服务端返回的快照替换本地视图。
- **操作定义为业务命令，没有"整图保存"。** 每条写命令带 `expected_revision` 做 CAS；同一案件的写入串行化（`case_change_seq` 行 `FOR UPDATE`）。冲突返回 409，客户端保留草稿、重新读取，不做"最后一次写入获胜"。
- **actor 由入口决定，调用方不能自报。** HTTP 入口固定 `human`/`local-web`，MCP 固定 `agent`/`mcp`，CLI 固定 `agent`/`cli`。服务函数据此决定变更记录是否进入"待确认"。
- **Agent 不通过浏览器操作业务数据。** 浏览器只用于验收与人工操作；Agent 走 MCP/CLI 命令入口。
- **每条命令在同一短事务内完成固定顺序**：进入写锁 → 锁定该案进度 → 同案与规则校验 → 节点 CAS → 写变更记录（修改前/后值与修订号）→ 变化序号 +1 → 审计 → 提交 → 返回快照。任一步失败整体回滚。
- **Agent 的修改默认待确认。** 变更记录 `review_state=pending`，承办人可确认（accepted）或撤回（reverted）。Agent 不能确认或撤回自己的修改；确认与撤回命令不在 `agent_commands` 白名单内。
- **撤回是一条新的反向命令。** 仅当受影响节点此后未再变化（修订号仍等于变更后的值）时允许，否则提示冲突由人工处理，不做半截撤回、不强制覆盖。已确认的变更也可撤回（支撑"一键全部确认"后反悔）。
- **变化序号驱动前端检测。** 前端轮询 `GET /cases/{id}/changes/seq`（默认 10 秒）并在回到前台时检查；序号变化才重新读取快照，迟到响应按请求序号丢弃。实时推送（LISTEN/NOTIFY）是后续增量，不改命令语义。

## 理由

命令化把"校验、变更记录、审计、序号"收敛到一处，三个入口天然一致；变更记录的修改前/后值同时支撑撤回、待确认复核与历史时间线，不必为每个用途各建一套。CAS + 行锁让单用户多入口（网页开着、Agent 同时在跑）也不会互相覆盖。

## 后果

- 新增操作 = 新增一条命令 + 服务函数 + 入口转换，不动表结构。
- 审计操作名是闭集（CHECK 约束），新增 `progress.*` 操作须同时在 `audit.OPERATIONS` 与迁移里登记。
- 前端 `useCaseProgress` 钩子与执行器接口同步/异步两用：P1 内存执行器与 P2 HTTP 执行器共用同一套组件，P4 替换传输层不改视图。
- 多用户协作需要用户与权限模型，另立项，当前不做占位接口（与 AGENTS.md 一致）。
