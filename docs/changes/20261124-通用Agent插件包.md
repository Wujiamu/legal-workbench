# 通用 Agent 插件包（Codex / DSH / MCP clients）变更单

状态：已实现待验收
基线：v0.1.0 + 0009_case_metadata（后继：[20261125-Agent访问硬围栏与授权收紧](20261125-Agent访问硬围栏与授权收紧.md) 已将 MCP 入口收紧为默认锁死＋单案授权，并将所有业务 Skill 前置了授权围栏）
最近更新：2026-11-25

## 1. 目标与范围

把素章（PlainFolio）从「手工填一段 `mcpServers` JSON」升级为可分发、可移植的 Agent 插件包，同时补齐实例发现机制，使插件包不必写死任何本机路径即可找到工作台：

- **实例发现与路径解耦**：工作台本体与插件启动器都按 `LWB_HOME` → `~/.plainfolio/instance.json` → 源码仓库根 的顺序解析安装目录；指针文件由 `scripts/lwb register-instance` 写入，只含路径与时间戳。
- **便携插件包**：`plugins/plainfolio/`（`plugin.json`、`mcp.json` / `.mcp.json`、三个业务 Skill、纯标准库启动器 `scripts/run-mcp.py`）＋本地插件市场清单 `.agents/plugins/marketplace.json`，同时兼容 Codex 与便携 Agent Plugins 格式（DeepSeek Harness / DSH 等）。
- **入口脚本**：`backend/pyproject.toml` 注册 `lwb-cli` / `lwb-mcp` / `lwb-doctor` 三个 console script，供插件在找不到虚拟环境时回退。
- **范围外**：不改数据库结构（零迁移）、不改网页、不做实机 GUI / 浏览器验收、不向真实 `~/.plainfolio/instance.json` 写入本机路径（测试全程用 `LWB_INSTANCE_CONFIG` 隔离）。

## 2. 关键决定

| 决定 | 理由 |
|---|---|
| `ROOT` 常量保留，且 `resolve_home_dir()` 在调用时读取模块级 `ROOT` | 既有 `test_windows_compat.py` 等通过 `monkeypatch.setattr(config, "ROOT", …)` 驱动 `load_settings()`；若在导入时捕获 ROOT，这批测试会失效（已做反向验证） |
| 指针文件只写 `home` / `project_root` / `updated_at`，`0600`，原子写入（临时文件 + `os.replace` + `fsync`） | 它是可读元数据而非凭据库；半写文件或崩溃不能把工作台卡死在「找不到目录」 |
| 指针里的 `home` 必须**已存在且是目录**才采纳，否则回退 `ROOT` | 换机器、移动仓库、删除目录后仍能启动；坏指针只降级不阻断 |
| 同时提供 `mcp.json`（便携，含 `$schema` 与 `type: stdio`）与 `.mcp.json`（Codex 兼容） | 便携格式自动发现根级 `mcp.json`；Codex 清单字段指向 `.mcp.json`。两者由测试守护内容不漂移 |
| `plugin.json` 同时带 `$schema` 与根级 `skills` / `mcpServers` | 声明便携格式（`$schema`），又保留 Codex 兼容字段。实测：`mcp.json` 完全通过 agent-plugins 1.0.0 `mcp.schema.json` 校验；`plugin.json` 的唯一偏差就是根级 `skills` / `mcpServers`（官方 `plugin.schema.json` 为 `additionalProperties: false`，便携包靠自动发现）。Codex 读到 `$schema` 时按便携包处理并自动发现 `skills/`、`mcp.json`，可能提示 `component_declaration_ignored`（预期告警，不阻断） |
| 启动器用 `os.execve` 而非 `subprocess` 转发 | stdio 直通，信号、stdin、stdout 不经中转；`LWB_MCP_AUTO_START_DB` 的 `start-db` 输出用 PIPE 捕获后只写 stderr，保证 stdout 只有 MCP 帧 |
| `start-db` 失败只告警、继续启动 | MCP 握手不应因数据库暂时不可用而失败；工具调用会返回结构化错误，客户端能看到原因 |
| 测试用 session 级 autouse fixture 把 `LWB_INSTANCE_CONFIG` 指向不存在的临时路径 | 否则任何跑过 `register-instance` 的开发机，其真实指针都会把 `load_settings()` 指向正式安装，令 `monkeypatch(config.ROOT)` 类测试假失败 |

## 5. 风险与未验证项

- **未做实机客户端验收**：未在 Codex / DSH / Claude Desktop 中实际安装本插件并跑通一次真实会话（本轮按红线要求不做 GUI / 客户端实测）。`plugin.json` 的 `$schema` 与 Codex 兼容字段并存时，`codex plugin validate` 可能提示 `component_declaration_ignored`；该告警已记入插件 README，但未实测其是否影响安装。
- **DSH `cordis.yml` 片段未实测**：字段名以 `dsh-mcp-client` / `dsh-agents-plugins-bridge` 的实际版本为准，README 已注明。
- **`${PLUGIN_ROOT}` 展开依赖客户端**：不展开占位符的旧客户端需改写为绝对路径，README 已给出两种写法。
- **`lwb-cli` / `lwb-mcp` / `lwb-doctor` 入口脚本未在本机重新安装**：本机为 editable 安装，`uv lock --check` 通过且未升级依赖；重新 `uv sync` 后才会生成 `.venv/bin/lwb-*`。启动器的 PATH 回退分支已用注入的 `which` 覆盖测试。
- **`docs/NEXT_STEPS.md` 未刷新**：本单状态为「已实现待验收」，尚未封板；按封板核对单，L0 总台刷新、CHANGELOG 流水与 L1 契约同步留待验收通过、正式应用时一并完成，避免与上一任务的未提交改动冲突。
