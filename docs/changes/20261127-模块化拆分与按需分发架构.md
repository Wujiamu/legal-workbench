## 使用场景

同一个工作台被三类用户使用：只要材料与检索的诉讼律师、要关系图与诉请金额的商事团队、只想拿两份方法论 Skill 去处理手上表格的同行。当前后端把全部功能编译进一个进程、MCP 一律暴露 57 个工具、网页导航一律显示全部页签——不用关系图的用户也背着它启动，接进来的 Agent 也总是拿到自己用不上的工具描述。

本变更把"要不要这个功能面"变成可配置项，并为后续把解析、卷宗导出拆成可独立安装的分发包铺路。**开关不是权限**：谁能看哪个案件仍由 [Agent 访问硬围栏](20261125-Agent访问硬围栏与授权收紧.md) 的默认锁死＋单案授权决定，模块只决定本机是否提供这个功能面。

## 三条已确认的架构决策

### 决策一：单仓库内独立 hatchling 包，由后端可编辑引用

把可独立分发的能力做成仓库内独立发行包：`packages/plainfolio-dossier`（卷宗导出）、`packages/plainfolio-parse`（文档解析），各自 `pyproject.toml` 用 `hatchling` 构建，版本独立演进。

后端 `backend/pyproject.toml` 通过 `[tool.uv.sources]` 以 `{ path = "../packages/<name>", editable = true }` 引用它们。这样做的理由：

- `cd backend && uv sync --locked` 仍是唯一的安装入口，`backend/.venv` 的布局与现有脚本（`scripts/lwb`、桌面启动器、PyInstaller 打包）都不变；
- 可编辑引用让本地改包即时生效，不需要每次重装；
- 将来把这两个包单独发布到私有索引时，只需删掉 `[tool.uv.sources]` 里的 path 覆盖，换成版本约束，调用方代码零改动。

反例（已排除）：把两个包做成同仓库的 `src/` 子目录 + 命名空间包，虽然最省事，但无法单独发布，也挡不住内部模块互相 import 到对方私有实现。

**风险**：`uv.lock` 会因 path 源改变而重写；打包脚本需要把两个新包一并收进冻结产物。Phase 2 必须在隔离环境验证 `uv sync --locked`、`pytest`、PyInstaller 冻结构建三处都通过后再应用。

### 决策二：Phase 0 → Phase 1 → Phase 2 → Phase 3 顺序推进

| 阶段 | 内容 | 为什么必须先于下一阶段 |
|---|---|---|
| Phase 0 | L2 变更单与 L0 登记 | 后面每一步都要有唯一的记录位置，避免"代码已改、口径没处写" |
| Phase 1 | 模块注册与开关（HTTP / MCP / 前端 / 独立 SOP 插件） | 开关是拆包的前提：先证明"能按功能面裁剪"，才知道该沿哪条缝拆包 |
| Phase 2 | 独立 hatchling 包 + `uv.sources` 可编辑引用 | 有了功能面边界，拆包才不会把跨模块依赖一起搬走 |
| Phase 3 | 零数据库独立 MCP（文件访问围栏方案 A） | 独立 MCP 只依赖 Phase 2 的解析/导出包，且没有数据库可依靠，围栏必须重新设计 |

每一阶段独立可回退：Phase 1 全部可关（默认全开＝现有行为）；Phase 2 只改依赖组织，业务代码位置不动；Phase 3 是新增进程，不替换现有任何入口。

### 决策三：零数据库独立 MCP 的文件访问围栏采用「方案 A」

Phase 3 的独立 MCP 没有数据库、没有案件概念，只有一个本地目录。围栏规则（本期**只固化决策**，不实现）：

- **默认只允许读写当前工作目录（CWD）及其子目录**；不做"全盘可读、禁止写"的宽松默认。
- 需要处理 CWD 之外的材料时，由用户在 `PLAINFOLIO_ALLOWED_ROOTS`（`os.pathsep` 分隔，Windows 为 `;`）里显式列出白名单目录；未列出的路径一律拒绝。
- 解析前对目标做**三重归一**再比对：`Path.resolve()` 消解 `..` 穿越、`Path.is_symlink()` 拒绝符号链接、Windows 上额外识别 NTFS Junction（`st_reparse_tag` / `os.path.isjunction`）并按链接目标判定。
- **原件只读**：输入文件只以只读方式打开；产物一律写到独立的输出目录，且**不得覆盖输入源文件**（同一路径写入即是错误，不是"覆盖前备份"）。

理由：零数据库场景下，Agent 与用户的材料之间没有"案件"这层隔离物，唯一可用的事实只有"用户把哪些目录交给了它"。默认收窄到 CWD，是把"授权范围"变成可见的一行配置，而不是靠模型自觉。

## 四层模块边界

| 层 | 模块 | 内容 | 依赖 |
|---|---|---|---|
| L1 底座 | `core` | 案件登记、材料导入与受管存储、解析任务、检索、出处读取、访问策略 | PostgreSQL + `var/data` 受管目录；任何裁剪都保留 |
| L2 案件记录 | `notes`、`progress`、`evidence`、`time` | 标注与分析版本、办案进度树、证据目录编号、工时记录 | L1 + 数据库；彼此不互相调用 |
| L3 图表与对外 | `graph`、`claims`（+ 图表导出） | 主体关系图、诉请金额、一源三态导出与审计包 | L1 + L2（引用材料与标注）；导出需 `graph` **或** `claims` 任一启用 |
| L4 分发 | 独立包与独立 MCP、`plainfolio-legal-sops` | `packages/plainfolio-dossier`、`packages/plainfolio-parse`、零数据库 MCP、通用方法论插件 | 不依赖 L1–L3 的运行时；方法论插件连代码都不依赖 |

跨层规则：L3 可以读 L2 的对象，L4 不得反向依赖 L1–L3 的内部实现（只允许依赖 Phase 2 拆出的两个公开包）。

## 业务规则与异常行为

- **未知模块名必须报错**：`LWB_ENABLED_MODULES=core,timeline` 直接 `invalid_input（未知模块：timeline）`，不静默丢弃——否则 `.env` 里一个笔误看起来就像"裁剪成功但功能没了"。
- **`core` 永远在首位**：只写可选模块也会自动补 `core`；`core` 之外的顺序按固定清单稳定排序，避免"同样配置、不同顺序"造成日志与测试漂移。
- **HTTP 层返回 `not_found` 而不是 `forbidden`**：裁剪后的本机确实没有这个功能面，`forbidden` 会被误读成"权限不足、去授权"，而授权在这里毫无用处。
- **`chart_export` 是并集**：`require_module("graph", "claims")` 任一启用即放行；两者都关时才 404，`details.modules` 如实列出两个名字。
- **MCP 默认行为不变**：不传 `--modules` 且 `LWB_MCP_MODULES` 未设置时，`build_server()` 直接返回模块级 `server`，工具清单与描述逐字相同。
- **裁剪不削弱围栏**：复制到新服务上的仍是 `@_case_guard` 包装后的函数，`_enforce_case_fence(新服务)` 在启动时重跑一遍；漏登记 `TOOL_MODULES` 的工具在裁剪时 `KeyError`，不会静默消失。
- **前端探测失败保持全开**：`/api/v1/modules` 404（旧后端）、请求被中止或单测未 mock 时静默保持全部启用，绝不因一次探测失败把用户锁在功能外。
- **禁用页签不可直达**：`?view=analysis` 在 `notes` 关闭时回落到材料页并改写 URL；`?ref=` 指向检索页，不受该回落影响。

### 一处有意的偏差（必须知悉）

需求写的是 `mcp>=1.30.0`，实现收窄为 **`mcp>=1.30.0,<2`**。原因：隔离环境 `uv pip install ./packages/plainfolio-dossier` 会解析到 mcp 2.x，而 2.x 把 `FastMCP` 改名为 `MCPServer` 并改了注册/运行语义——实测表现为服务进程 `ModuleNotFoundError: No module named 'mcp.server.fastmcp'`，客户端只看到 `Connection closed`（"启动即断开"）。工作台本身锁定 `mcp 1.30.0`，故为本包加上界，并让 `mcp_server` 在检测到 2.x 时打印明确的降级指令。迁移到 mcp 2.x 属独立变更，本轮不做。
