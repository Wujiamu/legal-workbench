# Agent 访问硬围栏与授权收紧（路线 2）

## 使用场景

通用插件包让任意 MCP 客户端都能接进工作台，但这也意味着**只要客户端启动，任何接入的模型就能列举整个案卷库**。工作台是离线单用户的，接进来的模型却不是承办人：它可能跑在云端、可能属于别的项目、可能只是同事临时打开的一个会话。真实案件一旦入库，一个默认放开的 `list_cases` 就等于把「本机有哪些案子」直接交给对方，`search_case` / `read_source` 再把正文递出去。

因此需要把「能不能看」从**默认允许**改成**默认禁止 + 按案授权**，并把授权动作牢牢留在承办人本人的终端上。

## 目标与范围

**做**：

1. 后端 / MCP 层默认锁死（`deny_all`）＋单案白名单硬门禁，零数据库迁移。
2. 全部带 `case_id` 的 MCP 工具（当前 52 个）在进入数据库之前统一过门禁；`list_cases` / `create_case` 单独收紧；新增只读自检工具 `get_access_policy`。
3. `scripts/lwb` 增加承办人本机专属的五个授权命令。
4. 全部面向用户的业务 Skill 前置同一段「授权前置与硬围栏纪律」。
5. 移除常驻型 DSH Cordis 插件（`plugins/dsh-plainfolio`），改走按需的通用 MCP 通道。
6. 文档同步与自动化测试（含全工具反射审计与真实 stdio 握手）。

**不做**：不改数据库结构（无迁移）；不改网页端（网页是承办人自己的界面，不受此门禁约束）；不做 GUI / 客户端实机验收（另列 NEXT_STEPS）；不引入任何新的第三方依赖。

## 方案与关键决策

### 为什么是「文件 + 环境变量取更严格者」

单案授权需要跨进程生效：MCP 服务由客户端拉起，是独立进程，内存里的开关传不过去；而写数据库又要迁移，且把授权状态塞进业务库会让「谁能看什么」和案件数据混在一起。落一个 `0600` 的小 JSON 在 `var/runtime/` 是最小面：无迁移、无凭据、可人工审计、可直接删掉即恢复锁死。

环境变量（`LWB_MCP_ALLOWED_CASES` / `LWB_MCP_ACCESS_MODE`）存在的理由只有两个：受控单案启动，以及测试。它们**只能放宽「根本没有策略文件」的默认**。一旦文件存在，取两者中更严格的：

- 文件 `deny_all` + 环境 `allow_all` → `deny_all`。否则某个 shell 里残留的变量就能撤销承办人刚执行的 `agent-lock`。
- 文件 `allow_all` + 环境 `allowlist` → `allowlist`。环境仍能把一次启动收窄到单案。

### 为什么门禁是装饰器而不是函数内检查

`_case_guard` 包在工具函数外面，`functools.wraps` 保留签名供 FastMCP 生成 schema。这样「先校验、后做事」不依赖每个函数体的写法；函数体里第一行就是 `_run(...)`，检查若写在里面，会话已经开了。

防漏网靠两道：

1. **导入期审计** `_enforce_case_fence()`：遍历已注册工具，凡带 `case_id` 却没有 `__case_guard__` 标记，直接 `RuntimeError` 让服务起不来。漏一个工具不是风格问题，是数据泄漏。
2. **测试期反射**：`test_agent_access_gate.py` 对每个带 `case_id` 的工具只传 `case_id` 调一次，断言全部 `forbidden` 且消息含 `agent-grant`。任何新工具只要忘了装饰器，导入就失败；就算绕过导入审计，反射用例也会红。

### 为什么 `list_cases` 在 `allowlist` 下不能复用原查询

原 `cases.list_cases` 先 `count(*)` 再分页。在 `allowlist` 下直接调用会把「库里有 37 个案子」这个事实返回给模型——**未授权案件的元信息本身就是涉密信息**（数量、增长节奏都能推断业务量）。所以新增 `cases.list_cases_by_ids`：`WHERE id IN (...)` 之后再 count 与分页，`total` 只等于已授权且确实存在的案件数。

### 为什么 `create_case` 单独管

建案不涉及既有案件，但它是**写入面**：一个能建案的 Agent 能在承办人的库里堆垃圾案件，且新建案件默认不在白名单里（等于建完自己也读不了，只会留下噪音）。因此默认拒绝，需要承办人显式置 `allow_create_case`。

### 为什么策略文件必须整份校验

早期实现只读 `mode`，`{"mode": "allow_all"}` 这种截断或手写的片段会被当成「全开」。现在要求四个键齐全、类型正确、UUID 全部可解析，任何一项不符即视为「没有可用文件」→ `deny_all`。安全默认值不能靠调用方补字段。

## 业务规则与异常行为

| 场景 | 行为 |
|---|---|
| 策略文件不存在 | `deny_all`，`source="default_deny"`；**不预生成文件** |
| 策略文件损坏 / 缺字段 / 含非法 UUID | 降级 `deny_all`，不报错、不崩服务 |
| `allowlist` 但白名单为空 | 规范化为 `deny_all`（`allow_create_case` 一并置 false） |
| `deny_all` 下 `list_cases(limit=0)` | 返回 `{"items": [], "offset": 0, "limit": 0, "total": 0, "mode": "deny_all"}` |
| `deny_all` 下 `list_cases(limit>0)`（含默认 50） | `forbidden`，消息含 `agent-grant` |
| `allowlist` 下 `list_cases` | 只返回白名单内且存在的案件，`total` 只计授权范围 |
| `allow_all` 下 `list_cases` | 原全库行为，不带 `mode` 字段 |
| 任意模式下未授权 `case_id` | `forbidden`；消息写明原因与本机命令；不含案件标题或元信息 |
| `case_id` 格式非法 | `invalid_input`（先于授权判断） |
| 已授权但库里不存在 | `not_found`（授权与存在性各司其职） |
| `create_case` 在 `deny_all` / 普通 `allowlist` | `forbidden` |
| `create_case` 在 `allow_all` 但未开 `allow_create_case` | `forbidden` |
| `LWB_MCP_ALLOWED_CASES` 含非法 UUID | `invalid_input`，显式报错，不静默丢弃 |
| `LWB_MCP_ACCESS_MODE` 值不在三档内 | `invalid_input` |
| `agent-allow-all` 不带 `--confirm` | 拒绝执行，退出码 2，不写文件 |
| `agent-grant` / `agent-revoke` 传非法 UUID | 拒绝，退出码 2，不写文件 |

## 实现要点

- `backend/src/legal_workbench/agent_access.py`：策略解析、原子写入（复用 `config._write_json_atomic`，`0600`）、`grant_case` / `revoke_case` / `lock_all` / `allow_all_cases`、`require_case_allowed` / `require_create_case_allowed`、`filter_allowed_cases` / `is_case_allowed`、`policy_summary`（供 `get_access_policy`）。
- `mcp_server.py`：`_case_guard` 装饰器覆盖 52 个带 `case_id` 的工具；`list_cases` / `create_case` 分支收紧；新增 `get_access_policy`；模块末尾 `_enforce_case_fence()` 导入期审计。**没有任何授权/解锁工具。**
- `cases.py`：新增 `list_cases_by_ids`（授权集合内的 count + 分页）。
- `scripts/lwb`：`agent-status` / `agent-grant` / `agent-revoke` / `agent-lock` / `agent-allow-all --confirm`。参数解析从 `len(sys.argv) != 2` 改为「首个参数 + 余下参数」，生命周期命令拒绝多余参数；授权命令不改工作目录、不碰数据库，若当前解释器缺后端依赖则转发到 `backend/.venv`（`LWB_AGENT_REEXEC` 防二次跳转）。
- `packaging/plainfolio.spec`：`hiddenimports` 增加 `legal_workbench.agent_access`。
- 五份 Skill（`plainfolio-workbench`、`legal-workbench-cli`、`chart-substantive-review`、`nonstandard-table-script-sop`、`legal-workbench-e2e-acceptance`，共 10 个文件）在正文最前面插入同一段「授权前置与硬围栏纪律」；镜像副本逐字一致。

## 移除常驻 DSH Cordis 插件

`plugins/dsh-plainfolio/` 整个目录删除（内容全部为本轮刚创建的源码、构建产物、依赖与测试，无任何用户业务数据；`git ls-files` 为空）。理由：常驻宿主插件会把「工作台在线、有哪些能力」变成一个长期存在的服务面，与「高保密案件按需授权、用完即锁」的隔离原则冲突。DSH 改为按需使用通用 `@deepseek-ai/dsh-mcp-client` stdio 配置，并受同一套默认锁死＋单案授权门禁约束。

`.gitignore` 中仅针对 `plugins/dsh-plainfolio/lib/` 的条目已清理；`plugins/**/node_modules/` 与 `packaging/` 的忽略规则保留。
