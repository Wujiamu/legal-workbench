# 法律工作台 V0.1 第二轮整改复审

日期：2026-11-13。复审结论：**本轮整改尚不能签收**。原先的索引提交间隙已关闭，普通上传去重、回归测试连接隔离等也通过了复跑。旧数据恢复、工作副本和材料切换仍有阻断问题。

## 审查发现

| 优先级 | 实测结果与根因 | 关闭标准 |
|---|---|---|
| P1 | **旧索引补发漏掉重解析，且可能选错版本。** 在同一文件版本生成两个 complete run，把活动指针恢复为旧 run，模拟旧程序在重解析终态后退出。正常启动 worker 后，新任务仍是 succeeded，活动指针仍指向旧 run。把活动指针清空重试，worker 也只补发了旧 run。补发查询排除了所有已有活动索引的版本，又按 sequence 升序取首个结果。[pipeline.py](../backend/src/legal_workbench/parsing/pipeline.py#L405) | 使用正常 worker 分别验证无活动索引及仍指向旧索引的旧数据，按发布规则选中应生效的版本。继续保护较新活动索引及历史 source_ref。 |
| P1 | **合法改名仍可把 DOCX 副本变成不可解析格式。** 将 `合同.docx` 改显示名为 `合同.v2`，创建副本得到 `合同（工作副本）.v2`。修改副本、登记并执行解析后，任务失败。后缀判断只检查字符形式，仍优先使用显示名，导致 `.v2` 被当作实际类型。[materials.py](../backend/src/legal_workbench/materials.py#L95) | 实际类型取基础版本，保留显示名中的版本号。加入无实际扩展名但以 `.v2` 结尾、以及显示名与实际格式不一致的用例，验证修改登记后可检索。 |
| P1 | **两次真正并行登记同一个已修改副本时，失败方绕过版本冲突处理。** 两个独立连接使用相同 revision，均确认修改后的字节尚无 StoredObject，再同时发布。实测一次成功，另一次在 StoredObject 写入时报 `uq_stored_objects_case_sha`，并留下一个无引用的版本文件。CAS 校验在该写入之后。原测试先等第一个提交，再调用第二个登记，第二个已经能复用第一个写入的对象。[materials.py](../backend/src/legal_workbench/materials.py#L195) · [并发回归](../backend/tests/test_register_concurrency.py#L38) | 让修订冲突发生在有副作用的发布之前，或妥善处理发布后所有相关失败。两个连接同步验证一个成功、一个返回 `conflict`、仅一个版本及解析任务、零无引用文件。 |
| P1 | **切换材料后仍会显示上一份材料的正文和副本。** 两条受控时序均实测失败。甲的提取文本在乙原件到达前返回，乙原件到达后，甲正文显示在乙标题下，直至乙正文返回。另一次在甲点击创建工作副本、切到乙，再让甲请求返回，乙详情中的「登记为新版本」变为可点，所用 ID 仍是甲副本。文本请求代次只在发新请求时推进，创建副本回包直接更新复用组件的状态。[MaterialDetail.tsx 正文](../frontend/src/components/MaterialDetail.tsx#L74) · [MaterialDetail.tsx 副本](../frontend/src/components/MaterialDetail.tsx#L127) | 将详情状态和请求归属绑定到案件及材料 ID。覆盖乙原件、乙正文各自延迟的情况，并验证甲副本回包不能启用乙详情的登记操作。 |
| P2 | **网页上传去重仍会生成无引用文件，两个并行批次也会撞唯一约束。** 同批上传字节相同的 `a.txt` 和 `a.md` 成功，库中只有一条 StoredObject，磁盘却多出无引用的 `source.md`。两连接同时上传同内容、同扩展名的独立批次时，一个成功，另一个撞 `uq_stored_objects_case_sha`。原因是按扩展名先发布文件，之后才以哈希查对象并决定插入。[imports.py](../backend/src/legal_workbench/imports.py#L378) | 顺序及并发上传都应让独立材料复用同一对象。验证同扩展名、异扩展名、同批和跨批，无孤立文件，两个合法批次都可完成。 |
