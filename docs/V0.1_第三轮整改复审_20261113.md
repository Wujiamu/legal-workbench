# 法律工作台 V0.1 第三轮整改复审

日期为 2026-11-13。**第三轮整改暂不能签收。** 本轮复现了三项 P1 和一项 P2，其中并行上传可能删除已经登记的共用原件。

## 复审发现

| 优先级 | 发现与独立验证 | 关闭标准 |
|---|---|---|
| P1 | **并行上传相同内容会删除共用原件。** 同案两个独立连接上传相同字节的 TXT，用同步屏障确保两个请求都完成物理发布后再写 StoredObject。两个批次都成功，数据库也只登记了一个对象，但对象校验失败。运行正常 worker 后，两份材料的解析任务均失败。保存点内发生唯一冲突后，失败方无条件删除路径。相同扩展名时，两个请求发布的是同一路径。原回归只检查「磁盘文件都在数据库中登记」，即使磁盘无文件也会通过。[上传去重](../backend/src/legal_workbench/imports.py#L397) · [原回归](../backend/tests/test_upload_dedupe.py#L140) | 同步到去重冲突点，确保两个批次均完成。逐个验证登记对象存在且哈希正确、原件可读、两份材料均可解析。分别覆盖同扩展名和异扩展名。 |
| P1 | **登记失败可能已提交新版本，再删除其内容。** 在实际登记流程中，让 `create_parse_run` 正常执行并提交，再在随后写入审计的调用点注入失败。新连接仍看到工作副本 revision=1、一个工作版本和一个排队任务，但文件校验失败。解析任务创建函数内部已经提交，外层回滚无法撤销，清理却仍删除文件。另用校验失败分支复现了登记失败、无工作版本、revision 已加一。[版本登记](../backend/src/legal_workbench/materials.py#L200) · [内层提交](../backend/src/legal_workbench/parsing/pipeline.py#L63) | 让登记的修订更新、版本和任务在同一提交点生效。分别在发布后、创建任务后、最终提交前注入失败，核对数据库与磁盘。完整性错误仍应报告，同时验证失败登记不会消耗修订号。 |
| P1 | **较新的部分覆盖结果会挡住应该补发的完整索引。** 同一文件先后有序号 0 和 1 的 complete run，活动指针仍停在 0，另外还有序号 2 的 partial run。正常启动 worker 后，指针实测仍停在 0，预期应更新到 1。修复只挑最新终态，遇到不允许覆盖的 partial 就结束，没检查其前面的完整结果。[补发候选选择](../backend/src/legal_workbench/parsing/pipeline.py#L427) | 补测「旧活动 complete → 漏发 complete → 更新 partial」及无活动指针的相应旧数据，核对应生效的索引、实际检索结果和历史引用。 |
| P2 | **切换材料后，编辑按钮会一直禁用。** 在甲点击「创建工作副本」，切到乙并等待乙原件加载完成，再让甲的创建请求返回。受控组件测试确认乙详情的「创建工作副本」仍禁用，保存和重新解析也共享该禁用状态。切换会作废甲请求，但没有重置 `busy`，甲的完成分支也不再复位它。[材料切换](../frontend/src/components/MaterialDetail.tsx#L50) · [创建副本完成分支](../frontend/src/components/MaterialDetail.tsx#L147) | 验证切换后乙可以继续操作，甲的迟到响应也不会启用乙的登记按钮或改变乙的状态。 |
