## 三、整改事项

### R01 — P1：解析不完整却显示完整

状态：待修复。

定位：`backend/src/legal_workbench/parsing/pipeline.py:89-98`，`_iter_units`；关联 `docx.py`、`xlsx.py`、`_unit_counts` 和解析发布规则。

**已确认行为**：DOCX 解析器会在 `ParseResult.warnings/status` 中报告页眉页脚、图片或文本框未提取；流水线仅转发 `result.units`，丢弃结果级警告。内存复现：有正文和页眉的 DOCX，解析器为 `partial`，警告为“页眉/页脚文本未纳入提取”；进入流水线统计后为 `complete=1、partial=0`。XLSX 的结果级图表/图片警告存在相同传递路径。

**影响**：网页与检索覆盖提示把未覆盖的内容报告为完整，用户可能把未命中理解为材料不存在。

**修复要求**：将结果级覆盖状态和警告传递、持久化到 ParseRun/覆盖输出，避免只检查单元级 warnings。不能靠把所有文件一律标为 partial 掩盖问题；保留真正完整文档的 complete 状态。新 partial 解析不能替换已有有效版本的既定规则也要保留。

**验收**：

1. 含正文和页眉的 DOCX 通过完整 pipeline 后显示部分覆盖，警告可追溯。
2. 含嵌入图片的 DOCX、含图表/图片的 XLSX 有相应覆盖提示。
3. 无上述未覆盖区域的普通文档仍可标 complete。
4. `get_index_status`、检索 coverage 和材料列表反映相同状态；不仅测试 parse_file 的直接返回值。

### R02 — P1：网页生成的工作副本扩展名失效

状态：待修复。

定位：`frontend/src/components/MaterialDetail.tsx:111-112`；关联 `backend/src/legal_workbench/materials.py:create_working_copy/register_file_version` 和 `storage.py:safe_extension`。

**已确认行为**：网页使用 `${material.display_name}（工作副本）`。`合同.docx（工作副本）` 的 `Path.suffix` 是非空的 `.docx（工作副本）`，因此服务端不会补回 `.docx`；`safe_extension` 将它转为 `.bin`。已内存验证 DOCX/XLSX/PDF/TXT 四种名称均出现该结果，`parse_file(source.bin)` 返回 unsupported_format。

**影响**：修改副本内容后登记产生新存储对象，其文件类型无法被解析。未修改内容就登记时会复用原始对象，所以“创建后立即登记成功”的旧测试不能覆盖此缺陷。

**修复要求**：工作副本标识放在合法扩展名前；实际类型应可靠地来源于基础文件版本，不应被任意显示名破坏。检查重命名后创建副本的路径，保持原件字节和历史版本不变。

**验收**：

1. 网页创建 TXT/DOCX/XLSX/PDF 副本，文件扩展名正确。
2. 实际修改副本内容、登记新版本、worker 解析成功，working scope 命中新内容，originals 不包含新增内容。
3. 对修改过显示名（无扩展名或含括号）的材料重复上述流程。
4. 原件哈希不变，未修改内容的去重复用仍正常。

补充：`expected_revision=0` 对刚创建的 WorkingCopy 是正确初值，本轮没有将这一点单独认定为缺陷。

### R03 — P1：解析完成与索引发布之间崩溃后漏发布

状态：待修复。

定位：`backend/src/legal_workbench/parsing/pipeline.py:270-271`；关联 `_finish`、`_publish_active`、`process_parse_job:208-211` 和 worker 恢复逻辑。

**已确认代码路径**：`_finish` 先提交 complete 和任务终态，随后才单独执行 `_publish_active`。两者之间退出，结果已完成但 active_parse_run_id 未更新；再次进入 process_parse_job 又因 complete 状态提前返回，不补做发布。任务已是成功状态时，普通 running 任务恢复也不会自动领取它。

**影响**：首次解析可能仍不可检索；重新解析可能永远查询旧版本，界面却报告任务成功。

**修复要求**：将终态与活动版本切换纳入同一可靠提交，或实现可恢复的明确发布阶段，选择最小可维护方案。必须同时保证旧任务晚完成不覆盖较新有效版本、partial 不替换已有有效版本及历史 source_ref 不失效。

**验收**：

1. 在“单元处理结束、任务终态、活动版本切换”各边界注入退出，并在新 worker/连接中恢复。
2. 首次解析恢复后可检索；重新解析恢复后命中新版本。
3. 不出现成功任务长期无对应有效索引且无错误提示的状态。
4. 旧 source_ref 仍返回原内容；已有的乱序发布、partial/failed 保留旧版本测试继续通过。

### R04 — P2：跳过已完成页面发生在实际 OCR 之后

状态：待修复。

定位：`backend/src/legal_workbench/parsing/pipeline.py:245-253`；关联 `pdf.py:iter_pdf_units/_parse_page`。

**已确认代码路径**：迭代器先解析并返回 ParsedUnit，调用方才检查 done_keys；指定页 OCR 时，其他页也是先解析，再用旧结果替换。因此数据库记录虽未重复，实际 OCR 仍可能重复。

**影响**：长扫描件恢复会重做已完成页面；原本无需重新处理的页可能因模型不可用等错误阻断恢复，违反“从未完成页继续”的承诺。

**修复要求**：在渲染/OCR 前决定跳过、复用或处理页面；不是处理完成后丢弃结果。复用未改页时保持完整的新 ParseRun 和新的 Segment ID，旧引用不受影响。

**验收**：

1. 含多页扫描内容的 PDF 在第 N 页后中断，恢复时用 OCR 调用计数证明已完成页未再识别。
2. 指定一页强制 OCR，其他已有有效页不调用 OCR，最终新版本覆盖整份文件。
3. 仅在被跳过页触发的模拟识别异常不会影响恢复；真正需要处理页的异常仍正确报告。
4. 至少一次真实本地 OCR 回归；测试替身计数与真实模型验证分别报告。

### R05 — P2：材料列表固定为前 50 份

状态：待修复。

定位：`frontend/src/pages/CaseWorkspacePage.tsx:54-75`、材料列表渲染。

**已确认代码路径**：请求始终为 offset=0、limit=50，没有翻页或加载更多控件；分类导航从当前页 materials 生成。

**影响**：超过 50 份的案件无法完整浏览。只出现在后续页的分类也不会出现在导航；筛选后分类导航和“全部”计数随筛选结果收缩。

**修复要求**：实现真实分页或加载更多；分类与全案总数独立于当前页和当前分类筛选。切换案件/分类时重置页码并处理当前选择，不以一次拉取所有材料替代分页。

**验收**：

1. 虚构案件至少 120 份材料，可到达第 51、101 份并查看原件、修改分类。
2. 仅出现在后续页的分类仍在导航中，分类切换后可以正常返回全部。
3. 全案总数与过滤后的结果总数含义正确，空分类与最后一页显示正常。
4. 浏览器实际操作验收，不能仅以 API 分页测试或前端构建成功代替。

### R06 — P2：切换来源时旧正文与新引用短暂混搭

状态：待修复。

定位：`frontend/src/components/SearchPanel.tsx:195-212` 的 SourcePanel，以及后续复制/保存引用控件。

**已确认代码路径**：选择新的 hit 后，组件保留旧 payload；新请求完成前，标题、source_ref 和保存表单已使用新 hit，正文仍来自旧 payload。此项是静态代码确认，未做本轮浏览器延迟复现。

**影响**：用户可能在切换期间阅读旧正文却复制或保存新材料引用，破坏来源对应关系。

**修复要求**：把正文与 source_ref 作为同一加载结果管理；切换时清空旧正文/错误/保存状态，或按引用重建组件；数据未就绪时禁用复制与保存。晚到响应不得覆盖当前选择。仅清空一次状态、但未防止响应乱序，不算完成。

**验收**：

1. 人为延迟来源读取请求，从A切到B期间不显示“A正文+B引用”。
2. 快速A→B→C并打乱响应次序，最终正文、标题、locator、复制引用和保存引用全部属于C。
3. B读取失败后不显示旧正文，也不能保存B引用与旧内容的组合。
4. 增加针对性组件测试，并做一次浏览器核对。
