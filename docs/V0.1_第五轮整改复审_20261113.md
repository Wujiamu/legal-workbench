# 法律工作台 V0.1 第五轮整改复审

2026-11-13。受检范围为当前法律工作台目录及第五轮交接。**上轮三项原始复现通过，当前版本暂不能签收。** 本轮补测发现一项 P1 和两项 P2。

| 优先级 | 触发条件、实测结果与原因 | 关闭标准 |
|---|---|---|
| P1 | **失败批次的回滚清理会删除另一批已登记的原件。** 同案批次甲先发布一份新 TXT，再因另一份既有对象校验失败而回滚。用同步事件把甲暂停在回滚后、删除文件前。批次乙在独立连接上传相同字节和扩展名，成功复用磁盘路径并提交。恢复甲的清理后，乙已登记的原件校验失败，正常 worker 拒绝解析。根因是回滚释放数据库事务后，甲按本批次的路径列表删除文件，此时乙已登记同一路径。[回滚与清理](../backend/src/legal_workbench/imports.py#L397) · [按内容发布](../backend/src/legal_workbench/storage.py#L277) | 保证同一受管路径的登记与清理互斥，或采用能安全重试的回收机制。复跑上述交错，甲应整批失败且原请求键仍可用，乙应保留有效任务、原件字节和可检索结果。 |
| P2 | **后续条目被拒时，前序发布文件留在磁盘。** 同批上传两个合法条目，再传入一个与第二条相同的相对路径。请求返回 `invalid_input`，新连接确认没有批次记录，磁盘却留有两份无引用文件。重复路径校验在发布循环中，文件清理只覆盖原件校验失败分支。[上传循环](../backend/src/legal_workbench/imports.py#L375) | 批次输入先做全量校验。对于发布后的实际失败，按同一批次失败语义收尾，保护其他批次已登记的路径，并验证重试和文件状态。 |
| P2 | **切走后成功的改名不会刷新材料列表。** 在甲发起改名并挂起响应，切到乙，随后让甲成功返回。乙详情未被污染，但回到甲仍显示旧名称和旧修订号。受控组件测试已将后续列表响应配置为新值，实际没有触发刷新。改名和分类共用这一结构，成功响应在归属检查处提前退出，跳过列表更新。此处实测的是改名。[改名成功处理](../frontend/src/components/MaterialDetail.tsx#L137) · [材料选择](../frontend/src/pages/CaseWorkspacePage.tsx#L85) | 当前详情只接收归属于它的反馈，成功写入仍应更新所属案件的列表。验证甲改名成功后切回即显示新名称与修订号，并保证乙正在进行的操作及状态不受影响。 |

独立复跑中，后端 **264 项通过**，配置的默认库仍为 0 张公开表。两份副本在实际发布点同步登记相同内容时均成功，零无引用版本文件。单批原件校验失败后没有留下半成品批次，现有 HTTP 回归验证了原请求键可重新提交。前端 **24 项通过**，类型检查与生产构建通过，现有分类迟到响应测试通过。新增的改名后切回测试在临时副本中失败。
